# Hardware Startup Investigation

Last updated: 2026-10-05

This is the running record for diagnosing unexpected attitude, swash, and
anti-rotation-motor movement during RAWES hardware startup. Keep new
observations, commands, and conclusions here so a later session can resume
without repeating unsafe experiments.

The current normative arm/disarm procedures, safe-off invariant, and verified
ArduPilot behavior are owned by [`design/arming.md`](design/arming.md). This
file is a dated investigation log; when a session changes the current model,
update both files in the same change.

## Session-maintenance instruction

During every investigation session, add any important new fact to this file
before concluding the session. Record the command used, connection parameters,
whether it was read-only or state-changing, the observed result, and the
current safety state. Distinguish measured facts from hypotheses, and update
the safe next steps or do-not-repeat list whenever the evidence changes the
plan.

Prefer fixing and instrumenting `calibrate` on the ground side during this
investigation. Do not update the deployed Lua script unless the evidence shows
that a ground-side change cannot solve or diagnose the issue. If a Lua update
becomes necessary, stop before deployment and provide the exact USB-only upload
procedure for the operator to perform manually; never upload the script over
the radio.

For MAVLink evidence, preserve the native raw capture and one canonical decoded
NDJSON file. `calibrate` attaches a `.mavlink.tlog.raw` file directly to
pymavlink's `logfile_raw`, which records received bytes before parsing. At
session close, `*.mavlink.jsonl` is generated by replaying that raw file
through pymavlink; no separate live NDJSON stream is merged into it. Read-only
`watch` sessions now capture the same raw and canonical logs, so startup
investigation does not require an armed run. When diagnosing a glitch, use the
raw capture to check whether malformed bytes or parser behavior could explain
missing decoded messages.

## Required safe-off state

After every diagnostic, leave the vehicle:

- disarmed;
- in ArduPilot `ACRO`;
- `RAWES_MODE=0`;
- `H_SV_MAN=0` (automated heli mixer);
- `H_FLYBAR_MODE=1` (ACRO RC passthrough);
- Lua mode 0 refreshing neutral RC1/RC2 and center-collective RC3 overrides while disarmed.
- `SERVO9_FUNCTION=0`, leaving the yaw motor output electrically unassigned.
- `H_YAW_TRIM=0`, preventing a stale prior-run motor trim when DDFP ownership
  is restored on a later run.

`H_SV_MAN=0` is required before an automated heli-control run. Disarmed alone
does not guarantee centered or electrically inactive swash outputs: with the
automated heli mixer enabled, ArduPilot can continue driving the swash.
Every normal/forced arm-disarm cycle and every calibration run exit must
converge on this exact state; cleanup code must not restore the yaw-motor
function afterward.

## What has been observed

### Startup/runup movement

The original passive startup entered GUIDED while traditional-heli runup was
still in progress. The startup was changed to:

1. set `RAWES_MODE=0`;
2. select ACRO;
3. arm;
4. wait for the configured heli runup;
5. enter passive/GUIDED only after runup.

This removed the obvious mode-ordering problem, but the armed runup itself
necessarily commands the main rotor throttle (`CH8` observed from about 1100
to 1900 us). `SERVO9` also showed a transient above 1000 us (approximately
1094 us in one run). This is real motor-command activity, not a harmless
visualization artifact.

Conclusion: a stationary bench test cannot validate the complete armed GUIDED
heli path while the motor remains connected.

### Passive handoff staging

The current staged passive protocol is:

- ACRO/runup with `RAWES_MODE=0`;
- passive thrust with absolute hold disabled;
- GUIDED_NOGPS transition;
- Lua commands zero body rate plus thrust while `RAWES_PEN` is disabled;
- passive yaw trim remains inhibited;
- wait for an `ACTIVE` heartbeat;
- wait for a quiet attitude-rate interval after EKF yaw-alignment events;
- capture the settled `ATTITUDE_QUATERNION`;
- send `RAWES_PEN=1` to enable absolute attitude/yaw hold.

This is intended to prevent an EKF yaw reset from producing a motor command
when absolute hold is enabled.

### 2026-09-23 passive-run evidence

The physically authorized passive run was:

```text

```

The run completed its automatic safety shutdown. The canonical evidence is
`simulation/logs/calibrate/run_passive_20260923_152536.mavlink.tlog.raw` plus
the NDJSON regenerated from it. This was an armed, state-changing test; the
setup was declared physically safe by the operator for that run only. The
vehicle was returned to canonical safe-off afterward.

Measured facts from the raw-derived log:

- `SERVO9` remained at or near motor-off, ranging from `1000` to `1039 us`.
  The observed movement was therefore not caused by a sustained SERVO9
  command.
- S1-S3 moved substantially immediately after passive absolute hold was
  enabled, for example approximately `1566/1428/1407 us` down to
  `1368/1503/1530 us` within about `0.5 s`.
- The Lua status text recorded a fixed passive command of
  `rpy=(74.6,22.5,112.5)` with `rr/pr/yr=(0,0,0)`.
- The actual `ATTITUDE_QUATERNION` at the first handoff sample matched the
  captured quaternion, but `ATTITUDE_TARGET.q` then slewed rapidly toward the
  requested attitude. Its reported target body rates reached approximately
  `5 rad/s` even though Lua's requested rates were zero.
- `ATTITUDE` changed continuously through the transition, including an Euler
  representation wrap near 90 degrees. The large Euler jumps are not by
  themselves evidence of a raw sensor discontinuity.
- The EKF event ordering was: ground magnetic yaw realignment for IMU0 and
  IMU1; quaternion/hold command receipt and absolute-hold enable; then
  in-flight yaw alignment complete approximately `0.68 s` later.
- The passive console's initial quaternion error was approximately `140 deg`.

The strongest current conclusion is that this is a target-transition/control
problem, not a sustained anti-rotation-motor command: switching from the
pre-enable `set_target_rate_and_throttle()` path to the angle-target path leaves
ArduPilot's internal attitude target to slew from its previous target to the
new fixed angle target. That internal slew generates the large S1-S3 response.
This is supported by the zero Lua rate command, changing `ATTITUDE_TARGET.q`,
large controller-generated target rates, and simultaneous SERVO9 motor-off
telemetry. It remains a hypothesis about the exact ArduPilot internal
transition because the current native raw capture is receive-only and does not
capture the outgoing Lua/NVF bytes.

Do not repeat an armed handoff merely to confirm this hypothesis. The next
ground-side diagnostic should instrument or qualify the handoff so the
attitude-target transition is visible before enabling absolute hold, or use a
no-motor/independently secured setup. No Lua upload was performed.
